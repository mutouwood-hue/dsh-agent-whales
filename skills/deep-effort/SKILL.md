# deep-effort：高预算执行

> 一句话：**效果优先。token 不是决策变量，结论必须有证据。**

## 一、成本立场（先定这条）

- **宁可多花几倍 token，也不要交一个没验证的结论。**
- 判断标准不是「花了多少」，而是「结论能不能被证据支撑」。
- 唯一仍然要避免的，是**没有信息增量**的动作——重复读同一文件、重复跑同一条命令，省的不是钱，是它不提高可靠性。

## 二、何时用 / 不用

- 用：任务链条长、结论要对外、弄错的代价 > 多花几倍 token 的代价。
- 不用：单点小改、查个字段、日常问答——直接标准模式，别过度。

## 三、四条硬要求

1. **先取证**。动手前把相关代码/日志/文档读到能写出「问题是什么、证据是什么」。没有证据的判断必须标「推断」。
2. **必须自验**。改完必须跑真实验证（测试/命令/接口/页面），贴真实输出。**没有验证输出 = 未完成**。
3. **不确定就多查多试**。读文件、查 wiki/Notion、问用户、写探针实验；不要猜。猜出来的结论要标注。
4. **交付前自检边界**。空、0、负数、超长、并发、失败路径，逐条过。

## 四、明确允许（很多人默认不敢做）

- 为把问题搞清而多读几轮、多翻几段历史、多跑几次实验。
- 复杂任务拆成独立子任务，**并行开子 agent**——允许，结果里说明谁做了什么。
- 真实复现 / 压测——允许，在临时目录进行、不碰生产数据。
- 主动扩大**取证范围**（读更多文件、跑更多验证），只要是为可靠性服务；但不要偷偷改变交付目标。

## 五、明确禁止

- 没有信息增量的重复劳动（不是为省钱，是它不提高结论质量）。
- 编造或转述未实际执行的验证结果。
- 把耗时长当成果好：以可验证的结论为准。

## 六、交付格式

```
结论（一句话）
证据（命令输出 / 文件:行 / 实测数字）
未验证的部分（明确写出来）
下一步建议
```
