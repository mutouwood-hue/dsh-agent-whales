# 需求主线：把零散功能串成一条业务流（设计稿；P0–P5 已实现，偏离与未做项见 §13）

来源：用户的画布 HTML《AI 产品工作台：从需求到验收的完整用户轨迹》（5 块画板）+ 对插件现状的核对（2026-11-18）。
状态：**设计待评审，尚未动代码**。动手前需先让其他会话停手（用户已答应），原因见 §9。

## 1. 问题

插件已有项目、任务、提案、画布元素（流程图 / 原型帧）、提问卡、`show_view`、串门、事件台，
但没有一条把用户行为串起来的主线：

- 没有「需求」这个实体，最上层是项目；
- 原型帧、流程图与任务、提案之间没有外键，只靠 `provenance.sourceMessageIds` 指向消息；
- 没有「确认设计 → 固化版本 → 交给任务」的机制（原型同一个 `prototypeId` 重画直接覆盖）；
- 没有 E2E 验收的产品功能（tabbit 只是开发者自测用）；
- 没有按需求聚合的总览（项目卡只有进度条和成员数）。

## 2. 已定决策（用户 2026-11-18）

1. **一个项目下多个需求**，类似主流 AI 产品里「项目 → 对话」。一个需求 = 一条要推进的事，有自己的 Composer 对话。
2. **本期做 E2E**。网页端 E2E 依赖 tabbit CLI，再补 computer use 补全无法用 DOM 驱动的部分。
3. **并行改动**：动手前用户会停掉其他会话；本方案仍按「新文件为主、旧文件只做局部替换」设计，降低冲突面。
4. **办公室保留**（趣味产品，独立页签）；**鲸鱼娘装饰层一定内置**，不拆成按需包；**MCP 约束层移到设置 › 高级**，画布上不再摆 MCP 节点。
5. **Univer 只做搭配，不嵌引擎**（2026-11-19）：画布仍用 React Flow，页面编辑仍用 Puck；需求的表格 / 文档附件交给官方 `dsh-univer-office` 插件产出，见 §12。
6. **精简范围**（见交互全景 ⑨）：砍经典画布、事件台、团队页、首次体验页、设置占位页；发送记录并入「活动」；任务 / 简报 / 执行并入画布与需求详情。一级菜单 6 → 3。

## 3. 一条线

```
澄清 ─▶ 设计 ─▶ 确认 ─▶ 开发 ─▶ 验收 ─▶ 通过
 │       │       │       │       │
Composer 原型帧   固化    T1/T2   E2E 带回截图
+提问卡  +流程图  设计版本 +依赖线  用户在图上批注
                                  └─▶ 回流：返工任务 / 回原型帧 / 回 Composer
                                         └─▶ 修好后自动再跑 E2E，直到全部通过
```

**阶段是推出来的，不是手填的**（同 `wbAgentSteps` 的思路，界面说的永远等于事实）：

| 阶段 | 判定（取自已有事实） | 总览颜色 |
| --- | --- | --- |
| 澄清 | 无原型帧、无提案 | 灰 |
| 设计 | 有原型帧，但没有已确认版本，或确认后原型又被改动 | 蓝 |
| 开发 | 已确认版本；该需求下有任务且未全部「已报完工」 | 蓝 |
| 验收 | 任务全部已报完工；最近一次 E2E 对**当前设计版本**未全部通过 | 琥珀 |
| 不符 | 最近一次 E2E 有失败且未处理 | 红 |
| 通过 | 最近一次 E2E 对当前设计版本全部通过 | 绿 |

“确认后原型又被改动”靠 `element.updatedAt > requirement.confirmedAt` 判定，不需要额外标记。

## 4. 数据模型（`projects.json` 加三张表，旧数据不动）

```
requirements[reqId] = {
  reqId, projectId, title, goal,
  composerSessionId,          // 该需求的主对话；也是项目成员（沿用“一个对话只属于一个项目”）
  revision,                   // CAS，同任务
  designVersion: 0,           // 当前已确认版本号，0 = 未确认
  designVersions: [{ v, at, by, hash, snapshot: { prototypes: {elementId: puck}, flows: {flowId: nodes} } }],
  reworkCount: 0, reworkCap: 3,
  createdAt, updatedAt
}
e2eRuns[runId] = {
  runId, requirementId, designVersion, taskIds[], driver: "tabbit-cli"|"computer-use"|"manual",
  status: "queued"|"running"|"passed"|"failed"|"error",
  results: [{ resultId, caseId, title, status, shots: [relPath], video?, log?, note,
              diagnosis: { kind: "code"|"design"|"requirement"|"env", reason, by: "ai" } }],
  annotations: [{ annId, resultId, shot, rect: {x,y,w,h} /*0..1 归一化*/, expected, by, at, handled }],
  startedAt, finishedAt
}
// 已有表只加可选字段：
task.requirementId, task.designVersion
element(prototype|flow).data.requirementId
proposal.requirementId
```

- 截图 / 录屏放 `~/.dsh/agent-whales/e2e/<runId>/`，库里只存相对路径；新路由按白名单下发（照 `art/*` 的写法：
  key 白名单、`immutable`+etag、路径穿越 404、大小上限）。
- **迁移**：老任务没有 `requirementId` → 归入每个项目自动生成的「未归类」虚拟需求，界面照常显示，不丢数据。
- 提案已有「版本号递增、确认后锁定」机制，设计版本照它做，不另造一套。

## 6. E2E：协议在插件里，驱动可插拔

插件**不内置浏览器驱动**，只定义协议和存储；谁来跑由一个「E2E 执行器」会话决定：

1. 全部任务已报完工 → 插件建 `queued` 的 run，并给执行器会话发一条交接（用例、设计版本、被测地址）。
2. 执行器（`dsh-agent-whales-worker` 的 E2E 变体 preset + 随包 skill）按用例跑：
   - 能用 DOM 的走 **tabbit CLI**（已有 skill，已被本仓库验证过）；
   - DOM 驱动不了的（原生控件、跨窗口、canvas 内容）走 **computer use**；
   - 每条用例调 `whales_e2e_report` 上报：状态 + 截图（插件把文件复制进 `e2e/<runId>/`）+ 日志 + 初判 `diagnosis`。
3. 全部通过且对应当前设计版本 → 需求变绿。有失败 → 红，进「需要我处理」。
4. **用户回流**：在实际截图上框选、写预期 → 点「回流」。按 `diagnosis.kind` 默认落点：
   `code` → `reopen` 对应任务；`design` → 批注钉回原型帧并把阶段拉回「设计」；`requirement` → 发给 Composer。
   用户可手动改落点。回流消息带截图、批注坐标、设计版本。
5. 返工完成、任务再次全部报完工 → 自动再跑。`reworkCount` 超过 `reworkCap`（默认 3）→ 不再自动回流，
   生成 `human_action`「建议回到需求重评」，对应 HTML 里的待定项。

**未验证 / 风险**：本机宿主里 computer use 工具是否可用、权限与沙箱如何，我还没有核实；
执行器会话在真实模型下是否稳定地调用 `whales_e2e_report` 也未验证（本仓库其他「agent 自己调工具」的链路目前都只有单测）。
所以驱动做成可替换，并保留 `manual` 驱动（人手动上传截图 + 标记结果）作为兜底，保证流程闭环不依赖 computer use。

## 12. 与 Univer 的结合点（只搭配，不嵌引擎）

**事实**（读 [univer README](https://github.com/dream-num/univer) 与 [dsh-univer-office README](https://github.com/dream-num/dsh-univer-office)）：

- Univer 是 Office SDK，不是节点画布。Apache-2.0 开源的只有 Web SDK 内核 + Sheets + Docs；Slides 与 Boards（它的「画布」）是单独授权的商业产品。
- 官方已有 DSH 插件 `dsh-univer-office`（Apache-2.0），给 agent 提供 `univer_new / univer_execute / univer_import / univer_export …` 等工具，产出 `.univer`、xlsx、docx、pptx；每次修改先进隔离草稿，由人确认或丢弃。
- 它依赖的 `@univerjs-pro` 等包的许可证与插件自身不同；商用前要自己读清楚，本方案不依赖这一点。

**怎么结合（零嵌入）**：

1. 需求的验收用例表 / 需求文档，让 agent 用 `dsh-univer-office` 产出文件，作为该需求的**附件**。
2. 附件靠我们已有的「文件 / 外部引用节点」（`GET /projects/:id/references`，只认会话日志里的事实）挂到对话上，再按需求归组展示，不做新的存储。
3. 不替换画布、不进页面编辑器、不进任务表格视图。

**已核实**：它的工具文件参数名统一叫 `file`（`univer_new` / `univer_execute` 的 `file` 字段），而我们 `REF_PATH_KEYS` 已包含 `file`，所以路径能被识别出来。

**需要小改的一处**：我们按工具名判断读 / 写，`REF_WRITE_TOOL` 目前不含 `univer_*`，所以 agent 用 `univer_execute` 改了表格，节点上会被标成「读过」而不是「改过」。落地时在判断里把 `univer_(new|execute|import|unit|worktree)` 算作写类。这是一个独立、很小的改动，排在 P1 里一并做，带单测。

**未验证**：

- 两个插件同装是否冲突（它声明会替换 DSH 内置的 `office*` skill，我们没有动这些，理论上不冲突）。
- 它声明支持的 DSH 版本是 `0.1.5-rc.3 / 0.1.7-rc.1 / 0.2.0-rc.1 / 0.2.1-rc.3`，我们要求 v0.2.1-rc.2 以上，交集只有 `0.2.1-rc.3`，用户的 DSH 版本需要对上。
- `.univer` 文件在草稿未确认前，磁盘上的文件内容是否已变化；这决定「改过」标记是否贴切。

**排期**：不进 P0–P5 关键路径。P1 顺带做上面那处工具名识别，其余等主线跑通后看你是否真的要用。

## 13. 实施记录与与设计稿的偏离（2026-11-19）

P0–P5、P6 第一刀与 P3 的六刀已落地（提交见 `git log 404b3dd..`，细节与真机证据见 README「需求主线」各节）。**偏离设计稿的地方，以及没做的地方，逐条如实记录：**

| 设计稿 | 实际 | 原因 |
| --- | --- | --- |
| §6.5 返工到上限「生成 `human_action`」 | 不生成任务级 `human_action`；需求阶段停在「不符」，待办类型 `rework-limit`（「返工超限」）进「需要我处理」，回流按钮禁用并提示「建议回到需求重新评审」，人仍可标「可接受」走出来 | `human_action` 挂在任务上、会进现有「worker 求人」组并被锁定；同一件事出现两条待办是重复。需求级待办已足够触达 |
| §10「多久没处理的需求升级提醒（默认 3 天，写事件台）」 | **没做** | 宿主没有可靠的定时钩子，事件台一节早已写明「本期不接定时来源」。硬做只能是进页面时才算的「假提醒」。需要先有宿主定时能力 |
| §10「状态色块按负责人筛选」 | **没做**（做了按阶段筛选） | 需求没有单一负责人，任务才有；要先定「需求的负责人」是什么 |

### 13.1 真模型验证（C1，2026-11-20）——找到并修了两个「单测全绿、真宿主上坏」的 bug

方法：桌面版 0.2.2-rc.5 的 `headless` profile（隔离 `DSH_HOME`，插件目录联接进去，模型路由同 web profile，密钥只放进子进程环境变量，不落盘不打印），
真模型（`step-5-preview`）、真宿主、真工具调用；被测运行与需求经**真实 HTTP 路由**创建（不手造数据）；证据截图由 Tabbit 对被测页取得。

1. **随包 skill 在真宿主上一个都加载不了**（影响 `deep-effort`、`whales-e2e-executor`、`whales-project-playbook`）。
   症状：模型调 `skill` 工具得到 `unknown or no longer available`，它的目录里也没有我们的 skill。
   两个根因，**都被我们自己的 `try/catch` 吞成一条告警**：
   ① 宿主 0.2.2 的 `registerProvider(create)` 要的是**同步工厂**，我们传的是 provider 对象 → `create is not a function`；
   ② 修了①之后仍不行：宿主在带 `AbortSignal` 的路径上 `promise.then(...)` 我们 `list()` 的返回值，我们返回的是同步数组 → `promise.then is not a function`，整个 provider 被跳过。无 signal 的目录展示路径恰好能走通，所以更难发现。
   修复：注册一个「既是工厂、又带 `name / list / get`」的函数（新旧两代宿主都能用），`list` / `get` 改为 `async`。
   **为什么单测一直绿**：旧测试的假宿主按「传对象、同步返回」写。现在的替身逐行抄宿主的 `registerProvider` / `waitWithAbort` / `validateCandidate` / `validateDefinition`，并断言带 signal 的 `list → get` 路径能加载三个 skill、正文真的读到。
2. **`whales_brief_read` 不带参数时被宿主拒收**：`INVALID_TOOL_OUTPUT: value is not lossless JSON`。
   原因：没有对话简报时返回里 `conversationBrief.updatedAt / updatedBy` 是 `undefined`。模型因此拿不到简报，只能绕路读需求。
   修复：在 6 个工具注册口统一把 `whales_*` 工具的返回值过一遍 JSON 往返（`losslessTools`），不逐个补；别的插件的工具不动。
   新增覆盖 12 个工具的「成功返回值深等价于 JSON 往返」测试；变异验证里发现「宿主 tools 服务是带私有字段的类实例，Proxy 转发不 `bind` 会抛」，已补用例。
